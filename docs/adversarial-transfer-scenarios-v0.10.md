# v0.10 반복 연결·사진 지연 적대적 시나리오

외부망은 범위에서 제외하고 Nearby 1:1 연결과 로컬 사진 전송만 다룬다.

| 상황 | 기대 결과 | 방어 장치 |
|---|---|---|
| 10초 썸네일보다 파일 전송이 느림 | 대기열이 무한히 늘지 않음 | 전송 중 1장 + 대기 중 최신 1장만 유지 |
| 대기 중 새 썸네일이 연속 생성 | 가장 최근 대기 사진만 남음 | 아직 전송을 시작하지 않은 이전 썸네일 폐기 |
| 파일 진행률이 15초간 그대로임 | 매체 승격 시간을 허용하되 막힌 payload를 계속 붙들지 않음 | `cancelPayload`, 2초 취소 응답 유예 후 로컬 정리 |
| 막힌 썸네일 뒤 최신 사진이 있음 | 실패한 옛 사진 대신 최신 사진 전송 | 실패 처리에서 옛 pending 삭제 후 최신 pending 시작 |
| 느리지만 진행 중인 Bluetooth 전송 | 새 썸네일이 생겨도 활성 파일은 중간 취소되지 않음 | 바이트 진행 시 15초 watchdog 갱신, 활성 파일은 완료까지 유지 |
| 연결이 끊긴 즉시 양쪽이 재검색 | 이전 Wi-Fi/Bluetooth 세대와 겹치지 않음 | 먼저 stop한 뒤 2초 무선 정리 시간 확보 |
| 재연결이 계속 실패 | 배터리·무선 API 호출 폭주 방지 | 2초, 4초, 8초, 16초 bounded backoff |
| 연결 성공 후 다시 끊김 | 다음 재연결은 다시 2초부터 시작 | Connected에서 backoff reset |
| 재연결 버튼 연타 | 예약이 여러 개 생기지 않음 | 기존 예약 제거 후 단일 restart runnable |
| FILE과 metadata 도착 순서가 바뀜 | 기존처럼 정상 결합 | payload ID correlation 유지 |
| 책 ROI/비교 사진이 큼 | 15초 안에 실제 진행이 있으면 계속 전송 | watchdog은 총 시간이 아니라 무진행 시간만 측정 |
| 일반 썸네일 용량이 지나치게 큼 | 눈·자리 확인 수준을 유지하며 전송 부담 완화 | 긴 변 1600px, JPEG 85; ROI는 JPEG 95 유지 |

실제 무선 매체는 Nearby가 선택하므로 앱에서 Wi-Fi Direct를 강제하지 않는다. 대신 느린 매체에서도 대기열이 누적되지 않도록 backpressure를 적용한다.
